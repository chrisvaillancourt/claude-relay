# relay

A Claude Code mod (function-hook plugin). A handoff saves a note and a continuation prompt to files through the `mcp__relay__handoff` tool, compacts when that turn ends, then delivers the prompt. `/relay` starts one with a save turn; the agent starts one by calling the tool itself. `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/prompts.ts`: pure text and parsing (`notePathFor`, `promptPathFor`, the tool's name, description and schema, `parseHandoff`, `savePrompt`, `composeContinuation`, `compactInstructionsFor`, the tool's answers, `withSession`, `runKey`, `isRunRecord`, `lostRunNotice`, `notCompactedNotice`, `forSubmit`, `isHeldOrigin`, `isPersonOrigin`, `teammateItem`, `holdAppend`, `restoreHold`, `heldNotice`, `isCanceled`, `parseArgs`, `withUnseen`, `stillUnseen`, `replacedText`, `supersededLine`). No `$`. Unit-tested in `prompts.test.ts`.
- `hooks/register.ts`: wiring. Hooks (`session.start`, `tool.call`, `turn.start`, `turn.complete`, `session.receive`, `session.append`, `prompt.submit`, `command.run`), the run's state machine, the hold, timers, logging.
- `types/index.d.ts`: types and the `$.state` contract (`PluginState['relay']`: `run` and `hold`, both `Shaped`). Every `$.state` key the module uses must be declared here; change the atoms' shape tags in `register.ts` when `Run` or `Hold` changes, so a value an older version stored reads as the initial one.
- `.claude-plugin/plugin.json`: manifest and `userConfig`. `marketplace.json` makes the repo its own marketplace.
- `.claude-plugin/types/` and `tsconfig.json` are generated by Claude Code when the mod loads. They're gitignored; don't commit or hand-edit them.

## Commands

```sh
claude plugin validate .
claude plugin test .
```

Both must pass before every commit. A behavior change needs a test in `hooks/*.test.ts` that fails without it.

## Design invariants

- **Engine constraints, found the hard way:**
  - `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
  - `$.session.compact` rejects while a turn runs, so the compaction starts from a timer after `turn.complete`. A rejection with no turn running is retried twice (interactive only) and logged to the debug log. Headless sessions reject it outright ("not available in a headless session yet"); there relay runs `/compact` through `$.command.run`, inline from the `turn.complete` hook, and submits (`submitLater`) without a timer, since the process exits before a timer fires; `/compact` run that way reports no skip, so a context that didn't shrink is taken for one, and with no size to compare with relay doesn't compact (taken from the checkpoint mod, checked there on 2.1.312; not yet run live from relay).
  - A plugin's submitted prompt never expands `@` mentions. That's why `fill` is the default delivery for a run the person starts, and why a submitted continuation leads with `forSubmit`.
  - The plugin, not the model, writes the handoff note (`$.fs.write` creates directories). A model `Write` outside the project raises a permission prompt. The note and the continuation arrive as the tool's arguments, so nothing is parsed out of the model's prose. (Earlier versions took the note from tags in the save turn's final message and drafted the prompt with `$.model.fork`, which is tool-less and saw only a quoted, cut copy of the note.)
  - `$.session.compact` runs through every hook but the calling plugin's, so relay can't answer its own compaction with the note as the summary. It steers the summarizer through `instructions` instead (`compactInstructionsFor`, over the text of `instructionsFile` when that file is set and readable, else `compactInstructions`; the file is read at each compaction and a failed read falls back, never stops the run). Read from the API types; not tested.
  - A teammate's message and idle notice raise no `prompt.submit` (checked live on 2.1.325, 2026-11-14). They raise `session.receive` with origin `{ kind: 'peer', teammate, isVerified }` and the bare text, and start a turn once the session is idle, even when they arrived while a turn ran. `{ consumed }` there keeps one out of the queue (stated by the types; the test kit shows it).
  - A delivery queued while no turn can take it (during a compaction, say) raises `prompt.submit` when it is dequeued, not when it is queued, and the engine dequeues as the session goes idle: for a compaction, the moment `$.session.compact` resolves. A subagent's hand-back is such a delivery (origin `{ kind: 'peer', from, handback: true }`, no `teammate`, so no `session.receive`). A plugin's submit is queued at the lowest priority (`queuePriority: 'later'`), behind all of them, and its promise seems to resolve only when its turn starts. So the hold must still be on when relay submits (`takeHeld`); releasing first let a hand-back or task notification start a turn ahead of the continuation, once by 33 minutes (transcripts of 2026-11-17 and 11-18, 2.1.326 and 2.1.327; the hook calls in those windows are inferred, since the debug logs had rotated).
  - A prompt the person types over a running turn raises `prompt.submit` at Enter with that turn's `turnId`, and is attached to the turn at its next step as an `attachment` row named `queued_command` (in transcripts its queue record is removed with `absorbed_mid_turn`; 2.1.326 and 2.1.327). That row reaches `session.append` on the **`delivery`** door, not `attachment` (checked live on 2.1.330 with an observer mod, headless stream-json, personal and Team accounts), so the hook matches `{ door: 'delivery' }`. Until 0.8.1 it matched `attachment`, taken from the row's `type` and the API types without a live run, and never fired. Task notifications and skip notices arrive on the same door as `queued_command` rows too; an unread entry leaves only when its own text (12 characters or more) shows in one. Whether one typed with `wait` set is attached too isn't known (the types say the engine queues it "either way"), so it is treated the same.
  - A queued prompt can't be withdrawn, and `turn.start` can't rewrite a prompt. `$.turn.abort({ turnId })` ends a running turn with no interruption marker (from the API types; not run live), which is how a replaced run's queued continuation is kept from running (`cutTurn`, from a timer after `next(e)`).
  - A compaction the person cancels rejects with "Compaction canceled."; `isCanceled` stops the run instead of retrying. The test kit can't make a mocked event reject with chosen text (a throwing hook is skipped and the kit's fallback error surfaces), so that rule is unit-tested as a pure function.
  - The engine already prefixes `$.ui.status`, `$.ui.toast`, `$.ui.log` and command output with the plugin name; don't add `relay:`.
  - **No guarantee rests on an event a seated plugin skips.** Where Claude Code seats the built-in `cc-plugin-sec-default` (Team and Enterprise accounts, managed settings or a managed MCP file, a managed `prependPlugins` that lists it), every `classic.*` event, `session.compact`, the prompt events (`prompt.section`, `prompt.context`, `prompt.attachment`, `prompt.compose`, `skill.prompt`), `attribution.text`, `settings.read` and `session.append` on the `attachment`, `hook-context` and `compaction` doors go past user-tier mods, and the engine reports each skip to the model as a `<task-notification>`. No relay hook is on a skipped event or door (the `session.append` hook is on `delivery`). Keep every `session.append` hook on a `{ door: [...] }` matcher that leaves out the skipped doors. The README's "Team, Enterprise and managed environments" section is the user-facing account: keep it in step.
  - `lastPrompt` in `$.store` is shared by every session (it's what `/relay paste` reads), so a run delivers its own prompt from the module (`runHandoff`) or from the file beside its note, never from the store: another session's run can overwrite the store mid-compaction.
- **Phases:** `idle → saving → armed → continuing → idle`. `saving`: `/relay` submitted the save prompt. `armed`: the tool call saved the note and prompt; the run waits for the main loop's next `turn.complete`. `continuing`: compacting and delivering. The agent's own call goes from `idle` straight to `armed`. Subagent and teammate turns and tool calls (`e.agentId` set) are ignored everywhere: on 2.1.312 they raise `turn.start` too.
- **Two sources, one path.** `run.source` is `person` (`/relay`) or `agent` (the tool called with no run). It decides delivery (`deliverMode`: the agent's run is always submitted, since nobody may be at the box), the `minTokens` floor (the agent's only), the clipboard (the person's only), and how a stop reaches the model.
- **The model is never left believing a compaction happened.** The tool's answer promises one, so every stop without a compaction corrects it (`notCompactedNotice`): the agent's run by relay's own submitted message, the person's run by `hold.notice`, which their next prompt carries as context (or by the hand-back message, when relay has held deliveries to submit first: `handBack`, used by `finish`, cancel and a reload's reset). Nothing depends on someone seeing a toast. A stop after a successful compaction (`isCompacted`) says nothing of the kind.
- **No step runs after a failed one.** A save turn that ends without the tool call, an interrupted turn, or a note that can't be written never compacts.
- **The person's prompt wins.** A person-origin prompt that arrives while the run is `saving`, `armed`, or `continuing` with no compaction in flight or done (`compaction`) and nothing in the box, stops the run; that prompt takes the notice and what's held. One that arrives while the compaction is in flight or after it is queued behind it; with the prompt in the box (`filledEarlyRunId`) it is taken for the continuation. A rejected compaction clears `compaction`, so the retry window counts as before the compaction.
- **A handoff call can be blocked for the rest of a turn** (`run.isBlocked`, in `$.state` so a reload keeps it; reset at each main-loop `turn.start`). Set by `/relay cancel`, by a person's prompt that stopped the run, by a save turn that starts with no `saving` run behind it (cancelled before it started), and by a restart that lost a `saving` run. Without it, the save prompt still in front of the model would start the agent's own run.
- **A handoff is never written without a prompt the model hasn't read.** A person's prompt typed over a running turn is listed in `run.unseen` (`$.state`) by the start of its text; a handoff call while the list isn't empty answers `UNSEEN_TEXT`. An entry of 12 characters or more leaves when its text shows in a `queued_command` row attached to the main conversation (`session.append`; a shorter one is in almost any row), the whole list at a refused call (`refuseUnseen`: the prompt reaches the model with that answer, so a build that never raises the row costs one refused call, not a blocked turn) and at each main-loop `turn.start`. This replaced a block for the rest of the turn, which refused the handoff a mid-turn prompt had asked for (2026-11-18).
- **A later handoff call replaces an unfinished run** (`arm`). In the handoff's own turn (`armed`), or while the compaction is in flight or the prompt is in the box, the call changes nothing (`ALREADY_TEXT`). In the turn a compaction waits for (`continuing`, `compaction` not this run's), `replaceHandoff` rewrites the note and prompt at the same paths and clears `isStale`. With the compaction done and the submitted continuation still queued behind a running turn (`continuing`, `compaction` done: `deliver` is awaiting its submit), the call starts a new agent run; the old continuation's text as submitted (`sent`) goes into `staleBodies`, and a turn whose prompt is exactly that text is cut short at `turn.start` (`cutTurn`, `cutTurnId`): that turn ends no hold, marks nothing stale, and its `turn.complete` (`aborted`) is not an interruption of the run waiting on it. Exactly, because a looser match (the lead and the old note's path) would also cut the new prompt when it lists the old note or the engine joins the two. The new continuation carries `supersededLine` and the held deliveries the old one carried (`replaced.held`), which are otherwise only in a prompt the model is told to ignore. A refused abort leaves the turn to run and marks the run `isStale`. A new run that stops or is cancelled (`dropReplaced`) removes the old prompt's entry, so that prompt runs rather than nothing; if it was already cut short or refused, the deliveries it carried are handed back instead. An old submit that's refused removes its own entry. `staleBodies`, `sent`, `replaced` and `cutTurnId` are module variables: a reload forgets them and the old prompt runs. Starting the new run depends on `deliver`'s submit staying pending while its prompt is queued (inferred from the 33-minute case; if it resolved when queued, the run would have finished and the call would start an ordinary run, with the old prompt still to come). Before this, a queued continuation kept the run `continuing`, the next call got `ALREADY_TEXT`, and its note was dropped (2026-11-17, 33 minutes).
- **A turn nobody typed is waited out, not fatal.** A message queued before the hold starts a turn the moment the handoff's turn ends. `compact()` then defers (`deferCompaction`, `waitingRunId`): the next main-loop `turn.complete` compacts. The run is marked `isStale`, and the delivered prompt ends with `STALE_NOTE`. More than `MAX_DEFERRALS` in a row, or a waited-for turn that's interrupted, stops the run. With the prompt already in the box, a turn since (running, or latched in `sentEarlyRunId` when it ended before a retry) is taken for that prompt's and stops the run instead.
- **The box is filled as compaction starts** (`fillDuringCompaction`, default on), so the person can queue the prompt before a background task finishes. So a failed or skipped compaction leaves the prompt in the box, and its message must say to run `/compact` before sending it. With the option off, a failed or skipped compaction fills nothing. That Enter during a compaction queues the prompt is the engine's behavior, which the test kit can't show and the API types don't state; Chris confirmed it by use (2026-11).
- **Deliveries are held** (`holdAtom` in `$.state`) from the tool call until the next main-loop `turn.start` after the continuation prompt. At `prompt.submit`, one whose origin `isHeldOrigin` and that carries no `turnId` (or carries one while no main-loop turn runs) is appended inside the atom update (`holdAppend`, so one racing a release passes instead of vanishing) and dropped. At `session.receive`, a teammate's delivery for the main conversation is appended as `teammateItem` and consumed, with or without a running turn. The person's prompt (`isPersonOrigin`) takes the items as `context` and sets `endsAtTurn`. Refused further down, `restoreHold` gives them (and the notice) back only if the hold's `gen` is unchanged (a cancel or new run bumps it) and only if that prompt was the one that set `endsAtTurn`. What arrives between that Enter and its turn's start is resubmitted as relay's message at that `turn.start`. A run that fails with nothing in the box, `/relay cancel` (any phase) and a new `/relay` (into its save prompt, taken when that prompt is sent, so a cancel first releases it) release what's held; a failed fill keeps holding. Any hand-back that's refused or fails goes to the log in full (`logHeld`): never lost silently. The items are mirrored to `$.store` under `held/<session id>` (`saveHeld`), since a consumed delivery is in no queue or transcript and `$.state` dies with the process; `session.start` in a new process hands them back (`restoreLostHeld`). A submitted continuation puts what's held in its own text, since a plugin's submit carries no context, and keeps the hold on (`takeHeld` sets `endsAtTurn`), so what arrives before its turn starts is resubmitted at that `turn.start` too; the run is finished only once that submit is accepted, and a refused one stops the run (for the agent's, with a message pointing at the prompt file). Not held: `unclassified` (a person's unstamped command shares it) and `channel` (maybe the person, remotely). Both hooks are fail-open (`.catch` lets the delivery through).
- **The continuation prompt is written beside the note** (`promptPathFor`) at the tool call: to compare with what was sent, and as the copy a run delivers from when a reload dropped the module's.
- **`saving` can't hang.** Five seconds after the save prompt's turn starts, a run whose save turn wasn't matched (`SAVE_MARKER` at `turn.start`) stops.
- **`runId` guards stale work.** Cancel and every new run bump it; each async step re-checks `isCurrent` before acting.
- **Hot reloads reset module variables** (timers included); `$.state` and `$.store` survive. `session.start` resets a run a reload left `continuing` (its timer is gone) and says where the note and prompt are, to the model too when the run was the agent's. A `saving` or `armed` run survives, since its next step is an event, not a timer.
- **A new process loses `$.state` too.** An upgrade can move a `--bg` session to a new process mid-turn (seen 2026-10-27 on 2.1.311 → 2.1.312; the transcript resumes with "Continuing an interrupted response", and `$.session.id()`, the transcript's name, stays the same). So each run in progress is also recorded in `$.store` under `run/<session id>` (`RunRecord`: its phase, note path, start and source), and every end of a run (`finish`, cancel, a reload's reset) deletes it. `session.start` with an idle `$.state` and a record for this session logs the lost run (`lostRunNotice`), toasts, calls `$.ui.notify` with the toast's text, and submits the notice to the model when the record's source is `agent`. The notify is fired with `void` and a `.catch`, never awaited, so a slow or failing channel can't hold up or break `session.start`. It's called unconditionally because a mod can't tell an attached session from a detached one (`$.session.surfaces()` reads `["terminal"]` in both); in a detached `--bg` session it resolves `no-channel`, but the person's settings `Notification` hooks still receive it as `plugin_notification` (checked 2026-10-27). Records older than a week are pruned at `session.start`. The engine gives no signal for a new process or a resumed turn, hence the record.
- Reporting is best effort and must never throw out of a hook or timer.

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`).
- Bump `version` in `plugin.json` for every release that GitHub installs should get; a folder-marketplace install reads the clone directly.
- MIT licensed: `LICENSE` at the root, and `plugin.json` says `MIT`. The repo is public, so keep personal paths, secrets and work details out of files and commit messages.
- Don't add Claude or AI attribution trailers to commits.
